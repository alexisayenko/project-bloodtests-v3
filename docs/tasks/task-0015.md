# Make the results tables usable on a narrow screen

Verbatim:

> for mobile app - usability. the top header and left header rows are
> auto hidden, but user can pull them (by edge or by scrolling). also
> when a user taps a cell - display the date and analysis headers only
> for that cell

Read as two changes on narrow screens: the date header row and the
marker-name column are hidden by default to reclaim scarce width,
revealable by a pull from the edge or by scrolling; and a tap on a cell
surfaces just that cell's date and analyte, instead of keeping both
headers permanently on screen.

## What the code says

- **Nothing in the tables is sticky or frozen today.** `ResultTables.tsx`
  renders an ordinary `<thead>` and an ordinary first-column `<td>`. The
  only `position: sticky` in the repo is `.header` in `index.css`, which
  belongs to the retired pre-nav flow (`archive/src/components/layout/
  Header.tsx`) and is rendered by nothing live. So "auto hidden … but the
  user can pull them" is not hiding an existing frozen header: it asks for
  freeze *and* hide *and* reveal, none of which exist.
- **There is a breakpoint, but it does not reach the tables.** `index.css`
  has one live media query, `@media (max-width: 767px)`, covering
  `.mc-page` padding, `.mc-nav` wrapping and the `.mc-panels-grid`
  two-column layout. (A second, `min-width: 640px`, styles `.main`/
  `.header` — both dead with the archive.) No component reads the
  viewport: no `matchMedia`, no width state, no touch handling anywhere
  outside the 3D chart's camera. Anything conditional on "is this a phone"
  needs that machinery introduced first, and that — not the gesture — is
  the real size of this ticket.
- **The table already scrolls horizontally, and the label column scrolls
  away with it.** Measured at a 375px viewport with the default five date
  columns and Scheduled on: the `colgroup` (180 label + 5×96 dates + 16
  spacer + 132 Scheduled) drives the fixed-layout table to 808px inside a
  351px wrapper, and the `overflowX: auto` div scrolls; the page body
  itself does not overflow. The reader sees the name column plus under two
  dates, and scrolling to a later date takes the marker name off screen.
  That is the complaint — and it argues for *freezing* the label column
  rather than hiding it.
- **Tapping a cell is already a two-stage gesture.** `armedCellHandler`:
  the first press selects the row and arms that (row, date) cell; a second
  press on the armed cell opens the popup; a cell with no value has no
  `onOpen` and so never leaves the arming step. Row selection is the same
  action, and it also drives the blue `RelationMark` gutter in Panel
  Detail. A third meaning for "tap" has to fit inside this or displace it.
- **The popup that second tap opens already shows the date and the
  analyte.** `ResultPopupBody` renders `test.full (test.short)`, then
  `formatMonthYear(entry.date) · entry.place`, then value + unit +
  reference; `IndexResultPopupBody` is the same with "Calculated". The
  requested information already exists — one tap later, inside a modal.
  What is missing is a cheap, one-tap, non-modal version of it, which
  makes this half of the request smaller than it sounds.
- **A mobile popup bug, found while checking that.** `popupPosition`
  (`ui.ts`) clamps left to `window.innerWidth - width - 8`; with
  `INDEX_POPUP_WIDTH` at 380 that goes negative below a 396px viewport, so
  an index popup hangs off the left edge on a phone. Fix here or split out.
- **Width pressure is still growing.** The Scheduled column (132px plus a
  16px spacer), the "Show observations from" panel select and the "Find a
  marker" filter all landed today, and Panel Detail stacks an Indices table
  on the same shared grid.

## Outcome

Partly shipped 2026-09-09 in `1d4dbf3`. The header-and-column half is
built; the per-cell tap is not, and the popup bug recorded above is
still live — so this stays open, narrowed to those two.

### Built

- **The label column is frozen *and* collapsible — both answers at
  once.** `TableScroller.tsx` now wraps every results table
  (observations and both indices tables); on mobile the real first
  column is `position: sticky` at a negative `--mc-col-left`, so it is
  the rows' own cells and cannot drift out of line with them.
  Unscrolled it sits at its natural 180px; scrolled it parks at a 5px
  sliver you drag or tap back open. That settles **hide or freeze**:
  the measured problem — the name scrolling away — is fixed by the
  freeze, and the requested hiding is what the frozen column does while
  you are not using it.
- **The date row is a fixed overlay copy.** Vertical sticky would
  resolve against the scrolling box rather than the page, so the reveal
  renders the *same* `colgroup` and `thead` in a fixed box of the same
  width with the table's horizontal scroll mirrored onto it, which is
  what lands its column edges on the body cells beneath.
- **"Pull them" was settled as: pull along the axis the thing left by,
  plus a button.** `usePullReveal` follows the finger, commits past 40%
  of the remaining extent and springs back otherwise; a gesture under
  6px counts as a tap on the sliver and toggles. The axis conflict was
  resolved rather than sidestepped — the header handle carries no
  `touch-action` and claims each `touchmove` only in the direction that
  moves the panel, so a page scroll started on it still scrolls. The
  control people are meant to find is the floating **Dates** chip
  (thumb-sized, riding the header's own moving edge); the pull is the
  shortcut.
- **The breakpoint keys off width.** `useIsMobile`
  (`web/src/hooks/useIsMobile.ts`) reads `matchMedia('(max-width:
  767px)')` — the established breakpoint, exported as `MOBILE_QUERY` so
  the JS-mounted overlays exist exactly where the CSS that places them
  applies. A narrow desktop window gets the behaviour too.
- **Hiding is visual only, as required.** Nothing is conditionally
  rendered: the real `<thead>` and the label cells stay in the DOM with
  their roles and tab stops. (The header reveal is a second, visible
  copy of the `thead`, so the accessibility tree now carries two — not a
  breach of the requirement, but worth knowing.)
- **Beyond the ask: the nav gets out of the way too.**
  `useHideOnScroll` + `NavBar` — on mobile the nav is fixed, slides off
  going down the page and returns going up, and publishes its height as
  `--mc-nav-h` / `--mc-nav-offset` so a revealed header parks under it
  instead of behind it. `prefers-reduced-motion` drops every transition.

### Not built

- **Tap a cell to reveal that cell's date and analyte.** Untouched:
  `armedCellHandler` and `isCellArmed` are unchanged and no strip,
  caption or per-cell label was added. The central open question —
  whether the tap gains a stage or replaces one — was never settled, so
  options (a), (b) and (c) below all still stand. Retrieving both
  headers by pull covers the same need less directly; whether that is
  enough to drop this half is a decision, not an oversight.
- **The `popupPosition` clamp bug.** Still live. `ui.ts` clamps left
  with `Math.min(Math.max(center - width / 2, 8), innerWidth - width -
  8)`, and the `Math.min` runs last, so with `INDEX_POPUP_WIDTH` at 380
  an index popup gets `left: -13` at a 375px viewport. Nothing in
  `1d4dbf3` touched it. It wants its own ticket — it is a plain bug
  rather than a design question, and it must not ride out on this one.
- **No tests.** `usePullReveal`, `useHideOnScroll`, `useIsMobile` and
  `TableScroller` carry no coverage; the suite is 586 passed / 1 skipped
  across 22 files, a count this work did not move.

### Settled elsewhere

Two of the width questions were answered by neighbouring commits rather
than here: `328bb5c` lays a panel card's rows in two columns on phones,
and `0f7bc36` / `acd29db` gather the filters into one control bar above
the tabs. The Scheduled column's 132px is untouched and still costs the
width the measurement charged it with.

## Open questions — settled by the build, or still open

- **Does the tap gesture gain a stage, or replace one?** This is the
  central design question. Options visible in the code: (a) make the
  *first* tap — which today only arms — also show that cell's date and
  analyte in a light strip, keeping the second tap for the popup; (b) drop
  the arming stage on narrow screens and open the existing popup on the
  first tap, since it already carries date and name; (c) leave the gesture
  alone and echo the armed cell's headers somewhere passive, e.g. a caption
  above the table. Each choice also changes what row selection and the
  `RelationMark` gutter mean on a phone, because arming and selecting are
  one action.
- **Hide, or freeze?** The measurement says the pain is that the label
  column *scrolls away*, not that it takes up room. `position: sticky` on
  the label cell and on `<thead>` fixes the stated problem with no gesture
  at all. Confirm whether hiding is genuinely wanted, or was a guess at how
  to buy width.
- **What does "pull them" mean, mechanically?** A horizontal edge drag
  competes with the browser's own back-swipe on iOS and Android *and* with
  the table's horizontal scroll, which owns the same axis; a vertical pull
  competes with page scroll. If the reveal has to be a gesture, pick the
  axis and edge first — a button or a remembered toggle sidesteps the
  conflict entirely.
- **Hiding must be visual only.** `<thead>` and the row label carry the
  table's meaning for screen readers and the accessibility tree, and every
  cell already has `pressable`'s role and tab stop. So this is clipping /
  offscreen positioning, never conditional rendering.
- **Which breakpoint, and does it key off width?** 767px is the
  established one. Decide whether the behaviour follows width, a coarse
  pointer, or an explicit setting — and whether a narrow desktop window
  gets it too.
- **What else does not fit at 375px?** Scheduled and the controls row were
  sized for the desktop layout. Whether they stay, collapse or drop out on
  narrow screens belongs to this decision, not to a follow-up.
