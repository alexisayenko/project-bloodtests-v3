# Reconcile lab-reported observations with their app-computed index twins

## What / why

Five clinical figures can, in principle, arrive two ways: printed by the
lab as an observation with its own LOINC, and/or cross-calculated by the
app's own index engine (`indexDefs.ts`/`computedIndices.ts`) from other
inputs — eGFR, ACR, LDL-C, cFT (calculated free testosterone), and
HOMA-IR. Today these two sources are not reconciled at all: at best they
render as two unrelated rows in different sections of the same results
table, with no link, no discrepancy flag, and no path from "I see two
numbers" to "I've dealt with it."

Proposal (Alex's own words):

1. When a marker is reported by the lab (exists as an observation with
   its own LOINC), display it in the Results table as normal (under
   Observations).
2. Clicking it opens a popup showing BOTH values side by side: the
   lab-reported value + its printed reference range, AND the app's own
   cross-calculated value + range (computed the normal way from the
   app's own index engine/inputs).
3. Mark the row/chip with "[!]" when the two values are meaningfully
   inconsistent.
4. From there, the user should be able to navigate to the underlying
   diagnostic report and: (a) delete that report's observation entry, if
   they confirm it's a lab mistake; (b) edit/update the report entry's
   value; (c) "accept the discrepancy" — mute the alert, i.e. record that
   they've reviewed it and it should stop being flagged (their call on
   which value, if either, is "correct" — the app doesn't have to
   auto-resolve, just stop nagging).

## What the code says (grounded findings per marker)

**eGFR** (LOINC `48642-3`, catalog `analyses.json`) — lab-reported only.
`computedIndices.ts`'s own header comment is explicit: *"Age/sex-dependent
indices (eGFR x3, FIB-4) are intentionally NOT ported; eGFR stays the
lab-reported LOINC value it already was."* No CKD-EPI (or any other)
formula exists anywhere in `indexDefs.ts` or `computedIndices.ts`. This is
a **hard prerequisite gap**, not something this task can build around —
there is no second value to reconcile against yet.

**ACR** (Albumin/Creatinine Ratio, LOINC `9318-7`, catalog `analyses.json`
— `friendlyName: "Albumin/Creatinine Ratio"`, `shortName: "ACR"`) —
lab-reported only. No formula, no `IndexDef` entry, no mention anywhere
in `indexDefs.ts`/`computedIndices.ts`. Same **hard prerequisite gap** as
eGFR — ACR is not itself computable from other observations the way
LDL-C or HOMA-IR are (it's a direct ratio of two measured urine values,
not a modeled estimate), so this may not even be the right shape of
problem for ACR; worth challenging in scoping rather than assuming a
formula is missing by oversight.

**LDL-C** — both `ldlf` (Friedewald) and `ldls` (Sampson/NIH eq. 2)
already exist as computed indices in `indexDefs.ts` (Cardiovascular Risk
panel), confirming CLAUDE.md. `ldlf` carries `loinc: '13457-7'` in its
`IndexDef` — and `13457-7` ("LDL Cholesterol by calculation") is *also*
the generic code labs use for their own calculated LDL-C, typically
Friedewald-derived (per `computedIndices.ts`'s `MARKER_LOINC['LDL-C']` and
the `remnant` index's own comment: *"the LDL-C subtracted is whatever the
lab reports under LOINC 13457-7 — the 'by calculation' code... so TC −
HDL-C − LDL-C reduces algebraically to that same TG/5 VLDL-C estimate
whenever the lab's LDL-C is Friedewald-derived"*). `ldlf`'s own prose
already tells the user, in text, to *"Compare it with the lab-reported
LDL-C row: a gap means the lab used a different method, not that your LDL
moved"* — i.e. the product intent this task is chasing is already
half-written into the index's copy, just not built as UI. `ldls` has no
`loinc` field at all — *"No LOINC code exists for a Sampson/NIH-equation
LDL-C, so this index has none."*

Despite `ldlf`'s `loinc: '13457-7'`, **the app does not currently connect
the lab-reported observation and the computed index**: `PanelDetailView.tsx`
filters `observations = tests.filter(t => !INDEX_LOINCS.has(t.loinc))`,
and `markers.ts`'s `INDEX_LOINCS` set is only `{'9830-1', '2502-3',
'48642-3'}` (TC/HDL, %Iron Saturation, eGFR) — `13457-7` is not in it, so
the lab's raw LDL-C renders as a normal Observation row, and `ldlf`/`ldls`
render separately (and additionally) under Cardiovascular Risk's Indices
section. Two rows, no link, confirmed.

**cFT** (`cft`, Vermeulen, Hypogonadism panel) — computed only. Its
`IndexDef` carries `loinc: '103227-5'`, but that LOINC has **no entry at
all** in `web/public/data/analyses.json` — the catalog doesn't know its
name, unit, or anything else about it, so even a lab that printed a
calculated free T under that exact code would render as an unrecognized
observation today. The catalog's only testosterone-adjacent lab-reported
LOINC is `2991-8`, "Free Testosterone" — the *measured* (direct
immunoassay) value, a clinically different figure from a calculated one
(different method entirely, not "the lab did the same math"), already
distinguished in CLAUDE.md's Hormonal Pathways badge list and in `cft`'s
own prose (*"compare it with the measured Free Testosterone row, whose
direct immunoassay is unreliable"*). So cFT has no real lab-reported twin
today, only a placeholder LOINC nobody's catalog entry backs.

**HOMA-IR** (`homair`, Insulin Resistance / Pancreatic Function panels) —
computed only (Matthews 1985 model). Its `IndexDef` has **no `loinc`
field at all**, and no LOINC for HOMA-IR exists anywhere in
`analyses.json`. Fully unconnected; no evidence any lab in this app's
history has printed a coded HOMA-IR value — labs virtually never report
it as a discrete analyte, they report the two inputs (glucose, insulin)
that the app already turns into `homair` itself. Reconciliation may not
apply to HOMA-IR at all in practice.

### Existing cross-linking mechanism (the real structural gap)

The closest thing today to "this LOINC observation and this computed
index are the same clinical measurement" is the `loinc` field some
`IndexDef`s carry (`ldlf`, `nonhdl`, `vldl`, `ldlhdl`, `apobapoa`, `gi`,
`cft`, `fai`, `deritis`, `tchdl`, `tsat`) plus `markers.ts`'s
`COMPUTED_LOINCS = new Set(INDEX_DEFS.map(d => d.loinc).filter(Boolean))`.
But `COMPUTED_LOINCS` is only ever intersected against `INDEX_LOINCS`
(3 hardcoded codes), and its documented purpose is narrow and different
from what this task needs: *dedup a raw badge that would otherwise
double-render* (TC/HDL and %Iron Saturation are "also independently
reportable by a lab... kept here only so they never show as raw badges").
It has **no effect at all** for `ldlf`/`cft`/etc. because their `loinc`
values aren't in `INDEX_LOINCS`, and even where it does apply it's a
display-dedup switch, not a value comparison — no discrepancy check, no
popup, no threshold, nothing that looks at both numbers together. This
confirms the task's premise: **there is no general "observation X and
index Y are the same clinical fact, compare their values" mechanism
anywhere in the codebase.** `aliasOf` is the wrong tool too, as the
feature request correctly anticipates — it links unit/method variants of
the *same* LOINC family (e.g. HbA1c's mass vs IFCC code), never a
lab-value vs an app-computed value from unrelated inputs.

### No "accept/dismiss/mute an alert" precedent anywhere

Grepped the whole of `web/src` for `acknowledge`/`dismiss`/`mute`/
`override` — no matches outside this file. Every existing localStorage
key (`bloodtests_envelope_meta_v1`, `_imported_links_v1`, `_lang`,
`_medications_v1`, `_scheduled_v1`, `_shared_meta_v1`,
`_sidebar_collapsed_v1`, `_upload_v1`, `_view_settings_v1`) stores either
bulk data or a simple session/UI preference — none is a per-observation
or per-report user override/acknowledgement. **This task has to design
that storage shape from scratch**, not extend an existing pattern.

`backupArchive.ts`'s `USER_DATA_KEYS` (also read by `isUserDataKey` for
Clear-all-data) lists exactly which localStorage keys are real user data
that round-trips through Export/Import-all-data:
`RESULTS_STORAGE_KEY, ENVELOPE_META_KEY, MEDICATIONS_KEY, SCHEDULED_KEY,
VIEW_SETTINGS_KEY, SHARED_META_KEY, IMPORTED_LINKS_KEY,
SIDEBAR_COLLAPSED_KEY`. Any new "accepted discrepancies" key needs to
join this list (and get its own part in the backup zip, the way
`medications.json`/`scheduled-visits.json` do in `backupArchive.ts`/
`backupRestore.ts`) to survive Export/Import all data and Clear all data
consistently with every other piece of user state — otherwise an
accepted discrepancy silently reappears after a restore, which would be
a worse experience than not muting it at all.

## Structural proposal

- **Identity link**: a new explicit mapping (not the incidental `IndexDef.loinc`
  field, which stays scoped to its current dedup purpose) pairing an
  observation LOINC with the `IndexDef.key`(s) that compute "the same"
  clinical figure — e.g. `13457-7 → ['ldlf', 'ldls']`. Where a marker has
  no lab-reportable LOINC of its own for the calculated figure (cFT,
  HOMA-IR), there's nothing to link — those simply never surface the
  reconciliation UI, which is a fine, expected outcome, not a bug to
  route around.
- **Accepted-discrepancy state**: needs its own localStorage key (e.g.
  `bloodtests_reconciliation_v1`), added to `backupArchive.ts`'s
  `USER_DATA_KEYS` and given a part in the backup zip + restore path. Key
  design question (below) is what it's keyed by — report id + LOINC, or
  session id + LOINC + date, or LOINC + date alone — since a visit can
  recur and the same discrepancy could reappear on a later draw.

## Open questions

- **"Meaningfully inconsistent" threshold**: absolute delta, percentage,
  or a per-marker custom threshold (LDL-C in mg/dL vs a ratio-based index
  like HOMA-IR need different notions of "close enough")? No existing
  precedent in the codebase (the closest is index `cut`/`hi` band
  thresholds, which are a different kind of comparison — value-vs-range,
  not value-vs-value).
- **Where does `[!]` render**: the Observation chip, a synthetic combined
  chip, or (since the computed twin usually isn't its own visible row
  today, per the LDL-C findings above) does building this feature also
  change whether `ldlf`/`ldls` keep rendering as separate Indices rows at
  all once they're reachable from the observation's popup?
- **Delete-report-entry confirm strength**: the existing per-row edit in
  report detail already gates Save/Cancel; is a discrepancy-driven delete
  (framed as "confirm it's a lab mistake") the same confirm, or does
  data-loss warrant something stronger, closer to `HoldToClearButton`'s
  press-and-hold?
- **Acknowledgement scope**: one-time-per-draw (this date's reading only)
  or persistent-per-marker (stop flagging this marker anywhere, any
  date)? Affects the storage key shape directly.

## Prerequisite gaps — not this task's scope

- **eGFR**: no CKD-EPI (or any) formula exists. A computed eGFR twin is a
  separate, standalone task (needs age — v3's envelope doesn't carry
  birth year into per-draw age the way eGFR formulas need it; see
  task-0004's related sex/age-banding gap).
- **ACR**: no formula exists, and it may not be the right shape of
  problem to computed-index at all (it's a direct measured ratio of two
  urine analytes a lab reports together, not typically re-derived from
  other observations). Needs its own scoping pass before assuming a
  formula belongs in `indexDefs.ts`.
- **HOMA-IR** and **cFT already have formulas** — no formula gap for
  these two, only the missing identity-link/reconciliation-UI this task
  covers, and even then only cFT's `2991-8` Free Testosterone versus
  `cft` is a real same-lab-visit comparison worth showing (framed as
  measured-vs-calculated, not lab-vs-app-recomputing-the-lab's-own-number,
  since no lab-reported calculated-free-T LOINC is actually catalogued).

Given three of five markers (eGFR, ACR, and arguably cFT-vs-measured)
don't fit the "lab prints the same calculated figure the app also
computes" shape cleanly, recommend **scoping the first build to LDL-C
only** (the one marker with a confirmed, already-linked LOINC collision
and existing prose asking the user to do this comparison by hand), and
opening separate follow-up tasks for eGFR's and ACR's formula
prerequisites before extending reconciliation to them.
