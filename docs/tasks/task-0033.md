# Preview a report's content on the Diagnostic Reports list page, without leaving it to edit

Seeing what a diagnostic report actually contains — its observations —
currently requires navigating away from the `#reports` list to the separate
`#reports/<file>` detail page. Add a way to preview a report's content
directly on the list page, without moving editing there.

## What the code says

- `web/src/components/conditions/DiagnosticReportsView.tsx` (`#reports`) is
  purely report-level metadata today: its one table (around lines 243-277)
  has exactly five columns — a status dot, Date (`formatFullDate`), Lab
  (`group.place`), Observations (`group.itemCount`, a plain count), and a
  chevron — and the whole row is a `pressable` click target that calls
  `onOpenDetail(group.file)`. **No observation-level content (name, LOINC,
  value, unit) renders anywhere on this page** — confirming the premise:
  today the only way to see what's in a report is to open its detail page.
- `web/src/components/conditions/DiagnosticReportDetailView.tsx` is the
  `#reports/<file>` page, and it is edit-capable by construction: its
  `ReportResultsSection` (lines 46-59+) renders the observations table with
  editable cells (`onEditItem`, `applyFieldEdit`, `cellInput`/`FIELD_INPUT`
  styling), a "Cross-check LOINCs" action, Save/Cancel gating
  (`draftItems`/`isSaving`), and NLM lookup wiring via `useLoincCrossCheck`.
  There is no read-only mode switch in it — it is inherently the edit
  surface, which is why simply reusing it inline on the list page would
  blur the line CLAUDE.md draws ("editing stays exclusively on the separate
  `#reports/<file>` page").
- `DiagnosticReport` (the `group` type) and its `Result[]` items are already
  in scope on the list page (`sessions: DiagnosticReport[]` prop), so a
  preview needs no new data plumbing — only a new, read-only rendering of
  `group`'s observations.

## The ask

Add a way to see a report's observations (name, LOINC, value, unit — at
minimum) directly on `#reports`, strictly read-only, while the row's
existing click-through to `#reports/<file>` (or an explicit affordance
next to it) remains the only path to editing. Candidate UI, not
prescribed — pick or propose in review:

1. An expandable row (click the status dot or a disclosure chevron to
   expand in place, a second click or the existing chevron still opens the
   edit page).
2. A read-only preview modal/panel triggered by a secondary action,
   leaving the row click going to the edit page as it does today.

Open question: which affordance avoids colliding with the existing
row-click-to-edit behavior clearly enough that a user doesn't expect the
preview to be editable. Resolve this before implementation.
