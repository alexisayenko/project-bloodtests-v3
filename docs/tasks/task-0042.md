# Make the albumin-fallback choice a persisted global setting, not just a Hormonal Pathways toggle

## The problem

The 3-way "what albumin value to use when a draw has no same-draw albumin
reading" choice (`Don't use a fallback` / `Use the nearest measured
albumin` / `Use 43 g/L`, or `Use 4.3 g/dL` in US units) exists ONLY in `HormonalPathwaysView.tsx`, as
local unpersisted `useState`. Every other surface that computes cFT
(calculated Free Testosterone) or Bio-T (Bioavailable Testosterone) —
Panel Detail's Results tab, All Observations, Panel Detail's Charts tab,
What's-in-range (`LabExploreView`), and the Reference Book — has no
control at all and silently uses a hardcoded default. So the SAME index,
for the SAME draw, can show a different number depending only on which
screen you're looking at. This inconsistency is the actual gap — not
merely "the control is in the wrong place."

## What the code says

- `web/src/data/computedIndices.ts`: `DEFAULT_ALBUMIN_GDL = 4.3` (line 23).
  `albuminMolL(albumin_gdl?)` (line 25) returns `(albumin_gdl ??
  DEFAULT_ALBUMIN_GDL) * 10 / ALBUMIN_MW` — i.e. whenever the caller passes
  `undefined` for albumin, this silently substitutes 4.3 g/dL with **no
  caller-visible signal** that a default was used.
- `web/src/data/indexDefs.ts`: `cft`'s `fn` (line 272) calls
  `calculatedFreeTestosterone(m['T']!, m['SHBG']!, m['ALB'])`; `biot`'s `fn`
  (line 294) calls `bioavailableTestosterone(m['T']!, m['SHBG']!,
  m['ALB'])`. `m['ALB']` comes from `markersForIndex(def, resultsByLoinc)`
  (`computedIndices.ts` line 351), which only reads the SAME-DRAW
  `resultsByLoinc` map handed to it — there is no parameter anywhere in
  `computeIndex` / `markersForIndex` / `markerValue` to inject an
  out-of-draw or overridden albumin value. `computeIndex`'s signature is
  exactly `(def: IndexDef, resultsByLoinc: Record<string, Result>)` — two
  arguments, no override.
- Five call sites use this same `computeIndex`, all with only a same-draw
  `resultsByLoinc` and no albumin override: `PanelsGridView.tsx`,
  `Popup.tsx`, `exploreModel.ts` (What's-in-range), `ResultTables.tsx`
  (Panel Detail Results tab + All Observations), and
  `HormonalPathwaysView.tsx` itself. The Reference Book's cFT/Bio-T pages
  are static prose (`INDEX_DEFS`), not a live computation, so they carry no
  runtime albumin behavior to fix, only prose that should stay accurate to
  whatever default ships.
- **`HormonalPathwaysView.tsx`'s own 3-way select does not fully work
  today**, which matters for scoping this task: `resolveAlbumin()` (line
  149) correctly resolves a `prior` reading via `latestEntryBefore` +
  `markersForIndex(biot, resultsByDate[prior.date])['ALB']`, and that
  resolved value IS used correctly for two things — gating the badge to
  empty when `fallback === 'none'` and nothing resolves (line 196), and
  computing the SHBG-bound/albumin-bound pool visualization directly via
  `testosteronePools(inputs['T'], inputs['SHBG'], albumin)` (lines
  202–205, which bypasses `computeIndex` entirely). But the actual cFT/Bio-T
  **badge number** is computed at line 197 via `computeIndex(def,
  resultsByLoinc)` using the unmodified same-draw `resultsByLoinc` — so
  when `fallback === 'prior'`, the badge still silently falls through to
  `DEFAULT_ALBUMIN_GDL` inside `albuminMolL`, not the resolved prior
  reading. Only the `default` and `none` options behave as their labels
  claim; `prior` visibly changes the pools chips below the badge but not
  the badge itself. This needs fixing as part of (or explicitly deferred
  from) this task, not carried over silently into the global version.

  > **Update 2026-09-16:** both parts of this bullet are out of date. The
  > `prior` option became `nearest` (78f34cf): the numeric albumin reading
  > closest in days to the selected date on either side, a tie going to the
  > earlier, found by `resultsLookup.ts`'s `nearestEntryTo`, which replaced
  > `latestEntryBefore`. And the page's cFT (Vermeulen) and Bio-T no longer
  > call `computeIndex`: both come from the same `testosteronePools` solve as
  > the bound pools, fed the resolved albumin, so every option now reaches the
  > badges too. The gap stands everywhere else — the other `computeIndex` call
  > sites still get no fallback choice.

## The proposal

Promote the 3-way choice (`none` / `prior` / `default`) to a persisted
global setting, read by the shared index-computation path so cFT and Bio-T
compute consistently everywhere, not just in Hormonal Pathways' own local
calls. This requires:

1. Fixing the plumbing gap above: `computeIndex` (or a variant) needs a way
   to actually receive a resolved override value for an `optionalInputKeys`
   input like `ALB`, and `HormonalPathwaysView`'s `prior` option needs to
   route through it correctly.
2. Deciding where the setting lives — see open question below.
3. Wiring every `computeIndex` call site (`PanelsGridView`, `Popup`,
   `exploreModel`, `ResultTables`, `HormonalPathwaysView`) to resolve
   albumin via the shared setting instead of relying on `computeIndex`'s
   silent internal default.

### Open question: where does the setting live?

Two existing mechanisms, neither an exact fit:

- **`bloodtests_envelope_meta_v1`** (`data/envelopeMeta.ts`, surfaced in
  `AccountView.tsx`'s "Database details" card) — subject/sex/birthYear/
  notes, written into the export envelope. This is subject-*identity*
  data, not a calculation-input preference.
- **`bloodtests_view_settings_v1`** (`ui.ts`'s `loadViewSettings`/
  `saveViewSettings`) — `unitSystem`/`sampleLimit`/`compactPanels`,
  display preferences, part of the backup's `settings.json`. This is
  display prefs, not something that changes the underlying numbers.

The albumin fallback is neither: it's a calculation-input preference that
changes real computed values shown across the whole app — a new category.
Options: (a) add it to `envelopeMeta` since it's conceptually closer to
"how do I want my numbers computed" alongside sex/birth year; (b) add it
to view settings since that's the existing generic small-settings bucket;
(c) give it its own small persisted key. Not decided — pick per how it's
threaded into `computeIndex`'s call sites.

### Open question: what happens to Hormonal Pathways' own select?

Once a global setting exists, does Hormonal Pathways' select disappear
entirely (the page just reads the global setting, same badge/pools
everywhere), or does it become a page-level override on top of a global
default (e.g. "for this page only, temporarily use X")? Not decided.

## Other open questions

- Does this setting need to round-trip through backup export/import and
  Supabase cloud sync the way other settings do? Both candidate homes
  already ride existing sync paths today — `envelopeMeta` rides inside the
  export envelope (`lab_reports` column), `viewSettings` rides in the
  `settings` column (`web/src/supabase/sync.ts` selects
  `manifest, lab_reports, medications, scheduled_visits, settings`) — so
  whichever is chosen, sync is close to free. Confirm rather than assume.
- Should the default stay `4.3 g/dL` (matching what every non-Hormonal-
  Pathways surface silently does today) to avoid silently changing every
  existing chart/table number the moment this ships? Recommend yes unless
  there's a reason to change the clinical default at the same time — that
  should be a separate decision, not a side effect of this refactor.
