# Enable TypeScript strict mode across the three tsconfigs

This task's own estimate, from an engineering pass over the codebase on
2026-09-18: `web/tsconfig.app.json`, `web/tsconfig.node.json` and
`web/tsconfig.worker.json` have never had `strict`, `strictNullChecks`,
`noImplicitAny`, `useUnknownInCatchVariables` or
`strictPropertyInitialization` set. `tsconfig.app.json`'s `include` covers
`src/` only — tests are never type-checked by `tsc`, only by Vitest's own
type-stripping.

## Estimated surface area

- `strict` alone: roughly **40–120 diagnostics** — optional-chain-shaped
  patterns like `querySelector(...).x`, `ref.current.x`,
  `catch (e) { e.message }`, array `.at(-1)` / `[0]` access, JSON-derived
  interfaces, a few classes including one in the vendored `lab-explore.ts`
  (inside `src`, so it is type-checked today).
- `noUncheckedIndexedAccess` on top: roughly **200–400 more** diagnostics,
  since the catalog leans heavily on `Record<string, ...>` lookups (142+
  such declarations) without null-checking the result today.
- `!` (non-null assertion) already appears ~27 times in the codebase
  pre-strict, suggesting the author already codes in a strict-aware style —
  the real diagnostic count may run toward the lower end of the estimate.

## Sequencing

1. Enable `strict: true` alone in all three configs first. Land and
   stabilize that as its own commit/PR.
2. Only then, as a separate step, dry-run `noUncheckedIndexedAccess`:
   `npx tsc -p tsconfig.app.json --noEmit --noUncheckedIndexedAccess | grep -c error`.
   Decide then whether the count is small enough to adopt immediately, or
   needs its own follow-up task. Don't bundle both changes into one.

## Acceptance criteria

- `npm run lint` and `tsc -b` both clean with `strict: true` set in all
  three tsconfigs.
- `npx vitest run` unchanged — this is a type-only pass, no behavior
  change.
- Where a real null-safety bug is found while fixing a type error, fix it
  and call it out plainly in the commit message rather than silently
  patching around the type error with a non-null assertion.
