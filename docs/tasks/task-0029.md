# Add an edit mode to Scheduled Visits (date, observations) and show the month as a label when not editing

Two asks that land as one coherent task: (1) the "Planned for" month control
on the Scheduled Visits page (`#plan`) is always an editable `<select>`, even
though the page is meant to be a read view of what was scheduled elsewhere —
show it as a plain text label instead, editable only in an explicit edit
mode; (2) actually let someone edit a visit — its month, and which
observations/indices belong to it — from this page, since today that is
only reachable through the Scheduled column checkboxes in Monitoring
Panels / All Observations results tables.

## What the code says

- **`PlanVisitView.tsx`'s "Planned for" pill is `MonthSelect` unconditionally.**
  `VisitPlanCard` (`web/src/components/conditions/PlanVisitView.tsx:104-124`)
  always renders `<MonthSelect ariaLabel={...} month={visit.month}
  onSetMonth={onSetMonth} />` inside the pill — there is no view/edit
  distinction on this page at all, so the select is live and interactive
  every time the page is open, not just while intentionally editing.
- **`MonthSelect` is shared, deliberately.** `ScheduleHeader.tsx`'s own doc
  comment: "Shared by ScheduleHeader (in a results table) and PlanVisitView
  (in the 'Planned for' pill), so both edit the same underlying month." Any
  edit-mode work on this page should keep reusing `MonthSelect` for the
  actual editing control — only the *view*-mode presentation (plain text
  vs. select) is new.
- **The add/remove-rows affordance is explicitly NOT on this page.**
  `PlanVisitView`'s empty state says: "tick rows in the Scheduled column of
  Monitoring Panels or All Observations, or add a visit there with the +
  button next to it" — confirmed by `docs/tasks/README.md`'s sibling
  CLAUDE.md prose ("the add/remove affordances live only in the results
  tables, not on this page, since a page with nothing to plan has nothing to
  attach an 'add' control to"). That reasoning applied when the page had
  *nothing* to attach a control to; once a visit exists and is being shown,
  there is something to attach one to. This task revisits that call for
  observation/index membership specifically — visit *removal* (`onRemove`,
  in `ScheduleHeader`) already exists and is out of scope here.
- **The data layer already supports everything this needs.**
  `web/src/components/conditions/scheduled.ts` exports `toggleRow`,
  `toggleIndex`, `setScheduleMonth`, and `useScheduled()` already hands back
  `onToggleRow` / `onToggleIndex` / `onSetMonth` wired to `MedicalConditionsPage.tsx`.
  `PlanVisitView` is not passed `onToggleRow`/`onToggleIndex` today — only
  `onSelectLab` and `onSetMonth` — so wiring those two props through is the
  main plumbing change, not new logic. `planRows(visit.loincs)`
  (`data/visitPlan.ts`) is what turns `visit.loincs` into the row list this
  page already renders, so an edit-mode checkbox per row can reuse the same
  row list to decide checked/unchecked (`isRowScheduled`).
- **Toggling cascades exactly like the results tables today.**
  `toggleRow` re-derives indices from the resulting LOINC set
  (`deriveIndices`), and `toggleIndex` schedules its own input LOINCs — the
  same cascade CLAUDE.md documents for Monitoring Panels/All Observations.
  An edit mode built here for free-standing checkboxes (not a shared results
  table) needs to preserve that cascade rather than reimplement it — call
  the same `onToggle`/`onToggleIndex` handlers.
- **`MedicationsView.tsx` is the app's established Edit/Done pattern** (see
  `web/src/components/conditions/MedicationsView.tsx:132,169-172,190-203`):
  a `useState<boolean>('editing')`, a single `Edit`/`Done` `Button` that
  flips it, and the same table rendering either static `<span>`s or
  `<input>`/checkbox controls depending on `editing` — no separate edit
  screen or modal. `PlanVisitView` has no such state today; this task adds
  the same pattern to it, scoped per visit or page-wide (an open design
  choice below).

## Open questions

- **Scope of the Edit/Done toggle: per-visit or page-wide?** The page shows
  one visit at a time via `TabBar` when there are several. A single
  page-wide toggle is simpler; a per-visit toggle avoids editing a visit
  while looking at another's tab, at the cost of an `editing` set keyed by
  visit id. Medications has only one table, so it didn't have to choose.
- **What does the observations/indices editor look like in edit mode?**
  Options: (a) reuse `ResultsTable`'s existing Scheduled-column checkboxes
  by rendering a results table scoped to `visit.loincs` plus everything
  else available (heavy — pulls in the full results-table machinery this
  page doesn't otherwise use); (b) a lighter picker specific to this page —
  e.g. a searchable list of markers/indices with checkboxes, closer to
  `planRows` already used for pricing. (b) fits the page's existing "just
  this visit's rows" scope better and avoids re-deriving prices for markers
  not yet added.
- **Does removing the last row from a visit in edit mode also offer to
  remove the visit itself**, or does it just leave an empty visit (as
  today's `EmptyState` already handles when a visit has zero rows)?
