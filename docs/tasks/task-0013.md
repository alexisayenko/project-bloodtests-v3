# Reorganize the results controls area

Three changes to the control row that sits with the results tables, as
one piece of work because the second depends on the first:

1. **Drop the column-order toggle.** The "Oldest → Newest" /
   "Newest → Oldest" pill in
   `web/src/components/conditions/ControlsBar.tsx`, backed by
   `dateOrder` in `AnalysisSettings` (`ui.ts`).
2. **Put the Monitoring Panels filter in its place.** The "Show
   observations from" select added to `AllObservationsView.tsx`,
   which styles itself from that file's local `PILL`/`PANEL_SELECT`
   constants.
3. **Hoist the whole controls section above the tab strip**, so it
   sits between the `<h1>` and `TabBar` rather than inside the tab
   body.

## What the code says

- `dateOrder` is not only a pill. It is one of three fields in
  `AnalysisSettings`, persisted to `localStorage`
  (`bloodtests_analysis_settings_v1`) by `saveAnalysisSettings`, read
  back by `loadAnalysisSettings`, consumed by `visibleDatesOf` in both
  `PanelDetailView` and `AllObservationsView`, and — the part that is
  not local — accepted and validated as a share-link setting in
  `web/src/data/sharedMeta.ts` (`SharedMetaSettings.dateOrder`,
  parsed in `parseSettings`). It is covered in
  `web/test/ui-helpers.test.ts` and `web/test/shared-meta.test.ts`.
- The panel select is not currently in `ControlsBar`. It lives in
  `AllObservationsView`'s own filter row, next to "Find a marker",
  and the two were deliberately built as one row.
- `ControlsBar` is rendered inside the `analysis` branch of both
  views, i.e. already below `TabBar` and invisible on the other tabs.

## Open questions — settle before implementing

- **What is the order once the control is gone?** Fixed ascending
  (today's default) or fixed descending — nobody has said. Note that
  `sortedDates`/`visibleDatesOf` take the newest N first and then
  optionally reverse, so "which N" and "in which direction" are two
  separate decisions that the single toggle conflated.
- **What happens to the stored `dateOrder` and to the share-link
  field?** Three surfaces outlive the control: a value already in a
  visitor's `localStorage`, the `settings.dateOrder` field a
  `/d/<guid>.meta.json` may carry, and the tests asserting both.
  Removing a control while its setting quietly keeps steering the
  tables is the failure mode to avoid — decide explicitly whether
  `dateOrder` leaves `AnalysisSettings` and `SharedMetaSettings`
  entirely, or stays as an unexposed field.
- **Moving the panel filter into `ControlsBar` cuts against an
  earlier decision.** It was put in the view precisely because
  `ControlsBar` holds the settings *shared* by Panel Detail and All
  Observations, while a panel filter only means anything in All
  Observations. The move is what was asked for; the consequence to
  choose between is making `ControlsBar` context-aware (an optional
  panel-filter prop, rendered only when supplied) or leaving the
  select in the view and merely restyling the row so it reads as
  ControlsBar's third slot.
- **Does "Find a marker" follow the panel select?** They are one row
  today. Splitting them puts one filter in the controls section and
  one below it.
- **Hoisting the controls above the tabs makes them apply to every
  tab, not just Analysis.** "What's in range" already consumes
  `unitSystem` but not `sampleLimit`; Charts has its own From/To year
  selects. Decide whether controls that do nothing on the active tab
  stay visible, grey out, or hide.
