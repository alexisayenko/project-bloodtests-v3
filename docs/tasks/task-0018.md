# Add a Medications history section for tracking what was taken and at what dosage

> **Status (2026-09-11): done.** The section shipped 2026-09-10 as described
> under "Shipped so far"; what is listed as still open belongs to follow-up
> tasks. Two things changed after it: Scheduled Visits now sits between
> Monitoring Panels and Medications in `NAV_ITEMS`, and Account's "Export all
> data" / "Import all data" zip carries `medications.json`, so medication
> history does travel through that backup — still not through Export JSON,
> the envelope or share links.

Goal: a new top-level section in the persistent nav — alongside Get
Started, Diagnostic Reports, All Observations, Monitoring Panels and
Reference Book — where the user records medications over time: what was
taken, at what dosage, month by month.

The request, in the user's words:

> a new menu item - where user will be able to track his medication,
> dosage by months.

That is the whole of the intent captured so far. Everything below the
"Why" is an open question, not a design — nothing here has been decided.

## Why it belongs here

Lab values move with medication. A marker's history is hard to read
without knowing what was being taken at the time: a thyroid panel on
levothyroxine, ferritin under supplementation, or lipids on a statin
tell a different story than the same numbers untreated. Today the app
stores the numbers and nothing about the treatment context, so the
reader has to supply that from memory.

The obvious later payoff is overlaying medication periods onto the
charts — but that is explicitly **a possible follow-up, not part of this
task**. It would also reopen a decision already taken: the vendored
`lab-explore` component was adopted "deliberately generic-only (no
medication overlays, reference-band overrides, or data-quality
flagging)" ([`CLAUDE.md`](../../CLAUDE.md), Tech stack), and
[`docs/milestones.md`](../milestones.md) records the same scope at the
2026-08-26 entry: "generic-only scope (no medication overlays,
reference-band overrides, or data-quality flagging)". An overlay would
therefore revisit that decision and should carry its own task, and
probably its own ADR, rather than arriving as a side effect of this one.

## Open questions — resolve before building

- **What is a medication entry?** Free text the user types, or a coded
  vocabulary (ATC, RxNorm, something else)? A vocabulary buys
  deduplication, grouping and later chart matching; free text buys
  "type it and move on". Which does this app want, given the LOINC
  precedent for observations?
- **Is dosage structured or a string?** Structured (amount + unit +
  frequency) or a single free-text field like "50 mcg daily"? If
  structured, does the unit vocabulary follow the UCUM decision already
  taken for observation units
  ([adr-0007](../tech/decisions/adr-0007-ucum-as-the-unit-vocabulary.md)),
  or is that a different problem?
- **What is the granularity of a period?** Month, as the request phrases
  it ("dosage by months"), or arbitrary start and end dates? Does an
  ongoing medication with no end date need representing? What about a
  dose that changes mid-period — a new entry, or an edit?
- **Where is it stored?** Its own localStorage key (the way
  `bloodtests_envelope_meta_v1` holds envelope metadata), or inside the
  interchange envelope alongside `diagnosticReports`? If the envelope:
  that is a format change and needs its own decision — see
  [`docs/tech/interchange-format.md`](../tech/interchange-format.md) and
  the envelope ADRs
  ([adr-0006](../tech/decisions/adr-0006-envelope-schema-numbered-3.md),
  [adr-0012](../tech/decisions/adr-0012-envelope-version-is-a-major-minor-string.md)).
  Note that `contentHash` is currently computed over the
  `diagnosticReports` array only, which is itself a question if
  medications join the envelope.
- **Does it export and import with the rest of the data?** Export/Import
  JSON, the share-link payload, "Import replaces all stored sessions" —
  does medication history travel through all of those, some, or none?
  What happens to stored medications on an import that replaces
  everything?
- **Is it per-subject?** The envelope already carries subject metadata
  (subject / sex / birth year / notes). Is medication history a property
  of that subject, and does that change the storage answer above?

## Shipped so far (2026-09-10)

The nav section: a `medications` route at `#medications` and a
"Medications" `NAV_ITEMS` entry between Monitoring Panels and Reference
Book. It stays reachable while validation errors exist, like Get Started
and Reference Book, which settles that question below.

The section itself (`MedicationsView.tsx` over `web/src/data/medications.ts`):

- **View mode** — one table: Medication, Dosage, then per shown year a
  year header spanning twelve month columns Jan–Dec, years in
  chronological order, inside a horizontal scroll container. A taken
  month is a filled cell; an empty state prompts Edit.
- **Edit mode** (the "Edit" button, reading "Done" while active) — name
  and dosage become text inputs, each month cell a `role="checkbox"`
  toggle labelled like "Metformin, Mar 2026", "Add medication" appends an
  empty row and focuses its name, "Add past year" adds the year before
  the earliest shown, and each row has a remove control. Leaving edit
  mode drops rows with an empty name; every change persists immediately.
- **Storage** — localStorage `bloodtests_medications_v1`,
  `{ years: number[], rows: { id, name, dosage, months: string[] }[] }`
  with `months` as ISO `YYYY-MM`. A missing or malformed payload loads as
  empty with the current year shown; the current year and any year
  carrying a mark are always shown; unnamed rows are dropped on load.
  Pure helpers and the `useMedications` hook, tested in
  `web/test/medications.test.ts`.

## Decisions taken (2026-09-10)

- **Storage:** its own localStorage key, not the interchange envelope — so
  no format change, and `contentHash` is untouched.
- **Travel:** none. Medication history is not exported, imported, or
  carried by share links, and an import that replaces all sessions leaves
  it alone.
- **Entry:** free-text name, no coded vocabulary.
- **Dosage:** one free-text string, not amount + unit + frequency.
- **Granularity:** the calendar month. A dose change is a second row
  with its own months; there are no start/end dates and no open-ended
  "ongoing" marker.

Still open: a coded vocabulary (ATC, RxNorm) for deduplication and chart
matching, structured dosage (and whether UCUM applies to it), whether
medication history should join export/import or the envelope (and so
whether it is per-subject), and chart overlays of medication periods,
which would revisit the generic-only `lab-explore` decision and should
carry their own task.

## Routing and nav work implied

Whatever the answers, the section itself follows the existing pattern in
`web/src/components/conditions/routing.ts`: a new `Route` variant, a new
hash in `routeToHash` / `hashToRoute` so browser back/forward works, and
a `NAV_ITEMS` entry with its label and its position among the five
current sections. The section then renders its own sibling view
component under `web/src/components/conditions/`, the way
`ProfileView` / `DiagnosticReportsView` / `AllObservationsView` do.

Worth deciding at the same time: whether this section is subject to the
existing "validation errors disable Monitoring Panels and All
Observations" rule, or stays reachable like Get Started and Reference
Book — medication entry has no dependency on report validity, which
argues for the latter, but it is a call, not an assumption.
