# Add lightweight authentication and optional server-side sync for two known users

Today the app is 100% local: no backend, all data in the browser's
`localStorage`, nothing leaves the device except the one explicit
NLM lookup and the optional `/?data=<guid>` share link
([`CLAUDE.md`](../../CLAUDE.md), Tech stack; ADR-0003). This task adds an
opt-in path to authenticate and sync across devices, for exactly two known
users, without disturbing that default.

## Motivation

Alex wants to simplify sharing this app between himself and his mother —
two known users, not public signup. There is no need for account creation,
password resets, or any of the machinery a general-audience auth system
would carry.

## Rejected approach

Full OAuth plus a managed backend (e.g. Supabase) was considered and
rejected. At two-user scale it is overkill, and worse, it contradicts the
app's whole privacy pitch ("your data stays in this browser") by
centralizing real health data in a third-party managed database by
default.

## Decided direction (2026-09-12)

### 1. Auth: Cloudflare Access + a client-side profile picker

The app already deploys as a Cloudflare Worker
([`CLAUDE.md`](../../CLAUDE.md), Tech stack). Cloudflare Access gates the
Worker — email/Google login via Access, no custom auth code to write or
maintain. Once Access has authenticated the request, the app shows a
simple profile picker client-side: "Alex" / "Natalya" (his mother). Access
identifies the *request*; the profile picker identifies *which user's
data* within it.

### 2. Storage stays dual-mode by default

- **Unauthenticated / local mode — the default, unchanged.** Exactly
  today's behavior: data lives only in the browser's `localStorage`, no
  login ever forced on anyone who doesn't opt in. This mode must remain
  fully intact and zero-friction. Nothing in this task makes login
  mandatory.
- **Authenticated / synced mode — opt-in.** Once a user authenticates via
  Cloudflare Access and picks a profile, the app talks to a small
  authenticated storage endpoint instead of `localStorage`.

Alex's stated preference is to host that endpoint on his own Hetzner box,
not Cloudflare KV/R2, specifically to keep health data under his own
infrastructure rather than a third-party platform — even though Cloudflare
storage would carry less ops overhead given the app is already deployed
there. This tradeoff was discussed explicitly; Hetzner was his call.

### 3. Migration model: a one-time cutover, not ongoing two-way sync

An initial suggestion of a continuous storage-adapter/sync layer with
conflict resolution was raised and **explicitly rejected by Alex** as
overcomplicated. The decided model is a ONE-TIME cutover on first login
per profile:

- **Server has no data yet for that profile**: push the browser's current
  `localStorage` data up to the server once. From then on the browser
  stops reading/writing `localStorage` for that profile — it is a client
  to the server, full stop.
- **Server already has data for that profile**: switch straight to the
  server's data. The browser's local data is not merged, not consulted,
  ignored entirely.

There is deliberately no ongoing conflict-resolution logic anywhere in
this design, because there is only ever one write path after the one-time
migration completes.

### 4. Open question — post-migration local-data disposition

After a successful one-time migration (local → server), should the
now-superseded local copy be wiped automatically, or left inert as a
fallback? Alex's answer: don't hardcode either — the app should **ask**
the user at migration time (e.g. "Data has been synced to your account.
Delete the local copy now?" yes/no), rather than the team deciding it
upfront. This is the one deliberately open question in an otherwise
settled design.

## Implementation surface (not yet scoped)

Listed for whoever eventually picks this up — open/unscoped, not
prescriptive:

- **A storage-adapter boundary.** The many existing direct
  `localStorage.getItem`/`setItem` call sites (results, `medications.ts`,
  `scheduled.ts`/scheduled visits, `backupArchive`/`backupRestore`, view
  settings, sidebar collapse state — see `CLAUDE.md`'s description of
  `USER_DATA_KEYS` and everything that currently lives in `localStorage`)
  need to be redirected to the sync endpoint once authenticated, without
  duplicating the app's data logic in two places.
- **The Hetzner-side endpoint**: auth verification via the Cloudflare
  Access JWT (e.g. the `Cf-Access-Jwt-Assertion` header) and per-profile
  JSON file storage.
- **The login / profile-picker UI.**
- **The one-time migration flow** and its wipe-or-keep prompt
  ([4](#4-open-question--post-migration-local-data-disposition)).

None of the above is designed yet; this ticket records the decided shape
of the problem, not an implementation plan.

## Update (2026-09-12): auth model superseded

Later the same day, further conversation re-opened the auth question
specifically and settled on something lighter than section 1 above:
[ADR-0015](../tech/decisions/adr-0015-dedicated-server-storage-via-bearer-token.md)
replaces Cloudflare Access plus the client-side profile picker with a
plain scoped Bearer API token the user pastes in, no login flow of any
kind. Sections 3 and 4 (the one-time-cutover migration model and the
open wipe-or-keep question) are unaffected and carry over into that ADR
unchanged. This section is appended for history, not a rewrite of the
above.
