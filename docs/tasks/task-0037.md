# Hide Get Started for signed-in users

Get Started (`#profile`, first in `NAV_ITEMS`) is onboarding: app
description, privacy statement, Import JSON, "Go to Diagnostic
Reports", and Generate Test Data. A returning, already-signed-in
user doesn't need it on every visit — but "signed in" and "has no
data yet" are not the same condition, and conflating them would
wrongly hide onboarding from a freshly-signed-in user with an empty
cloud account.

## What the code says

- `ProfileView` (`web/src/components/conditions/ProfileView.tsx`)
  already calls `useSupabaseAuthUser()` — today only to swap copy
  (description line, pillar icon: "Synced to your account" vs.
  "100% private"), not to hide anything.
- `NAV_ITEMS` (`web/src/components/conditions/routing.ts:21`) is a
  static array; `profile` is first. `isNavItemActive` /
  `isRouteBlocked` / `isNavItemBlocked` are the existing hooks for
  conditionally gating a nav item or redirecting a route — today
  gating is driven only by `hasValidationErrors`, not by auth or
  data state. `isRouteBlocked` redirects blocked routes to
  `#reports` (see `MedicalConditionsPage.tsx`, which swaps the route
  during render and replaces history so Back can't loop into it).
- `useSupabaseAuthUser` (`web/src/hooks/useSupabaseAuthUser.ts`)
  returns `{user, loading}` from `supabase.auth.getSession()` +
  `onAuthStateChange` — it reports only session state, nothing about
  whether that account's data has loaded.
- `TopBar.tsx` and `AccountView.tsx` both read the same hook the
  same way, for display only (a "Synced to your account" line/pill).
- The existing "has data" signal used elsewhere is `sessions.length`
  (diagnostic reports), read in `MedicalConditionsPage.tsx` and
  passed into `ProfileView` as `sessionCount` already — this is what
  drives report-count copy on Get Started itself, and what
  `isRouteBlocked` conditions ultimately key off indirectly via
  `validationIssues = validateDiagnosticReports(sessions)`. No
  existing code currently branches UI on "is this account new/empty"
  as distinct from "is `sessions` empty."
- Per ADR-0018/0019's sync model: sign-in either pulls existing
  cloud data (repopulating `sessions`) or, if the cloud row doesn't
  exist yet, pushes today's local data up as the account's first
  copy. So immediately after a fresh sign-in, `sessions` reflects
  whatever was true locally before sign-in (empty or not) — `user`
  being set does not imply `sessions.length > 0`.

## Open questions

- **Hide mechanism** — three options, not mutually exclusive:
  1. Drop `profile` from `NAV_ITEMS` (and phone `NavBar`) entirely
     when signed in — nav item disappears, `#profile` presumably
     still reachable by direct URL/history unless also redirected.
  2. Keep the nav item but redirect `#profile` elsewhere (e.g.
     `#panels`, mirroring how `isRouteBlocked` redirects blocked
     routes to `#reports`) when the hide condition holds.
  3. Keep the page and nav item, hide only the onboarding-only
     controls within it (Import JSON, Generate Test Data, "Go to
     Diagnostic Reports") while keeping the description/privacy/
     evidence-grading copy, since that's product framing a returning
     user might still want to see once.
  These aren't exclusive — e.g. 2 could pair with keeping the nav
  item visible but inert, or 1 could still leave `#profile` reachable
  by hand with no redirect. Needs a decision.
- **Signed-in vs. has-data** — is the real condition "signed in"
  (`user` truthy), "signed in AND `sessions.length > 0`", or just
  "`sessions.length > 0`" regardless of auth (i.e. the same signal
  `ProfileView` already receives as `sessionCount`)? A signed-in user
  with an empty cloud account still needs Import/Generate Test Data;
  hiding those on `user` alone would strand them. Using
  `sessionCount > 0` alone would also hide onboarding for a
  signed-out first-time local user who already imported data, which
  may or may not be desired — the ask specifically named "already
  signed in," so a data-only condition may not match intent.
- If a redirect is chosen (option 2), does it fire immediately on
  route change (like `isRouteBlocked`, via
  `history.replaceState`), or only as a "default landing route"
  choice made once at load (so a signed-in user can still navigate
  back to Get Started manually if the nav item stays)?
- Whatever the condition, should it also gate the "Get Started" nav
  item's blocked/redirect status through the same `isRouteBlocked` /
  `isNavItemBlocked` machinery validation errors use, or is this a
  separate, unrelated gate (auth/data state vs. validation state)
  that deserves its own function rather than overloading
  `isRouteBlocked`?
