# Display the signed-in account's name/email in the top bar

`TopBar` currently shows only a generic "Synced to your account" line when
signed in — no indication of *which* account. Show the actual name or
email.

## What the code says

- **`TopBar.tsx` (`web/src/components/conditions/TopBar.tsx:7-35`) reads
  only `{ user }` from `useSupabaseAuthUser()` and branches on truthiness** —
  `user ? 'Synced to your account' : 'Your data stays in this browser'`. It
  never reads any field off `user` itself, so no name/email plumbing exists
  yet; this is a small, additive change to the signed-in branch only.
- **`useSupabaseAuthUser` (`web/src/hooks/useSupabaseAuthUser.ts`) returns
  Supabase's own `User` type verbatim** (`import type { User } from
  '@supabase/supabase-js'`), sourced from `supabase.auth.getSession()` and
  kept live via `supabase.auth.onAuthStateChange`. Nothing narrows or
  reshapes it — `TopBar` (and any other consumer) has the full Supabase
  `User` object to work with, which carries (per Supabase's `User` type):
  - `email?: string` — always present for both providers this app wires up.
  - `user_metadata: { [key: string]: any }` — provider-supplied claims,
    populated by whatever the OAuth provider returns and not typed further
    by Supabase itself. In practice, for Google this commonly includes
    `full_name`, `name`, `avatar_url`, `picture`; Apple's own OAuth
    response is minimal by comparison and often carries only what the user
    chose to share (Apple's "Hide My Email" can also make even `email` a
    relay address) — so `user_metadata.full_name` / `.name` cannot be
    assumed present for every sign-in, and the display logic needs a
    fallback chain rather than reading one field.
- **`auth.ts` (`web/src/supabase/auth.ts`) confirms the two providers
  wired up are exactly Google and Apple** (`signInWithGoogle` /
  `signInWithApple`, both plain `supabase.auth.signInWithOAuth` with no
  extra `scopes`/`queryParams` requesting more profile data) — so no
  provider-specific scope change is needed to get *more* metadata than
  what's already being returned; the task is purely about reading what
  `user_metadata`/`email` already carries and picking a sensible display
  string and fallback order (e.g. `user_metadata.full_name ??
  user_metadata.name ?? email ?? 'your account'`).
- **No other component reads `user_metadata` today** (checked
  `AccountAuthCard`, `ProfileView.tsx`, `TopBar.tsx` — all three call
  `useSupabaseAuthUser` but only ever branch on the presence/absence of
  `user`, never its contents), so there's no existing convention in this
  codebase for which metadata field to prefer; this task is the first to
  decide it.
