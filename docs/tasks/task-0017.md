# Audit the computed-index unit fallback for unchecked values

`computedIndices.ts`'s `markerValue` has a fallback path: when an
index's `inputUnits` declares no expected unit for a given marker
input, and the reading in question sits on the analyte's *primary*
LOINC code, the printed numeric value is handed to the formula
as-is, with no unit check or conversion.

```ts
const primary = (MARKER_LOINC[short] ?? [])[0];
const to = target ?? MARKER_REFERENCE_UNIT[short];
for (const loinc of MARKER_CANDIDATE_LOINCS[short] ?? []) {
  const r = resultsByLoinc[loinc];
  if (r?.value == null) continue;
  if (!to) return r.value;               // <-- no expected unit: pass through raw
  const converted = convertUnit(r.value, short, r.unit, to);
  if (converted !== undefined) return converted;
  if (!target && loinc === primary) return r.value;   // <-- primary code: pass through raw even when conversion failed
  ...
}
```

The function's own doc comment names this as a deliberate,
inherited exception ("DHT is reported in pg/mL against a ng/dL code
and dhtt's formula rescales it itself"), but it is a blanket
exception, not a per-analyte one: it fires for *any* marker on its
primary code with no declared `inputUnits` entry, whether or not
that marker's index formula happens to tolerate the ambiguity the
way `dhtt` does.

## How this was found

Investigating why HOMA-IR, HOMA-%B, Glucose/Insulin ratio and TyG
kept computing correctly for an insulin reading printed in `µU/mL`
despite a units-folding regression elsewhere: none of those four
indices declare `inputUnits.Insulin`, so the raw printed number
reached the formula through this fallback. It happened to be correct
only because `µU/mL` and the unit each formula assumes coincide for
that analyte on its primary code. An insulin reading printed in
`pmol/L` — the SI unit, roughly 6x the µIU/mL number for the same
physiological value — would silently feed the wrong magnitude into
all four indices instead of being declined the way an out-of-range
or unplaceable value already is everywhere else in this codebase.

This is a data-trustworthiness gap in the sense
[`docs/concerns.md`](../concerns.md)'s draft "Make data trustworthy"
notes describe: normalization and LOINC cross-check are largely
done, but nothing here establishes that a value silently reaching a
formula is on the scale that formula assumes. `computedIndices.ts`'s
own doc comment on `markerValue` states the intended contract — "An
input that cannot be placed in the expected unit is left OUT rather
than passed through as printed, because a number on the wrong scale
would silently produce a wrong index" — and this fallback is the one
path that doesn't honor it.

## Scope

Audit every `IndexDef` in `web/src/data/indexDefs.ts` for marker
inputs (`inputKeys`) with no matching key in that def's `inputUnits`.
For each one found, either:

- **Declare the expected unit explicitly** in `inputUnits`, closing
  the gap the normal `convertUnit` path already handles for every
  other input — this is the fix for anything not shaped like `dhtt`;
  or
- **Confirm and document why raw pass-through is actually safe** for
  that specific marker (the `dhtt`/DHT case: the formula itself
  rescales, or the analyte has no other unit in practice) and leave
  a comment saying so, so the exception is legible per-analyte
  rather than accidental; or
- **Add an explicit conversion/decline path** if neither of the
  above applies — a differently-unitted reading should be converted
  or dropped (matching `markerValue`'s existing "left out rather
  than passed through" behavior for every other case) rather than
  silently trusted.

Start from the four indices that surfaced this (HOMA-IR, HOMA-%B,
Glucose/Insulin ratio, TyG — all sourcing `Insulin`), then check the
rest of `INDEX_DEFS` for the same pattern; don't assume Insulin is
the only affected marker.
