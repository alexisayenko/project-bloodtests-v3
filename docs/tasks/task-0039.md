# Decide on Observations/Indices naming (or an alternative split)

Alex's framing: "think about naming of Indices... I guess all of those
are observations? so maybe should we say 'measured' and 'derived'? or
'analytes' and 'calculations'? to research and think."

This is a research/proposal task, not a rename. It lays out options; it
does not pick one.

## The current split

[`docs/product/concepts/observation.md`](../product/concepts/observation.md)
and
[`docs/product/concepts/computed-index.md`](../product/concepts/computed-index.md)
already define two concepts precisely:

- **Observation** — a lab-measurable quantity identified by a LOINC
  code. "Not a result" (the definition, not a value); results carry
  the value.
- **Computed index** — "A ratio or estimate the product derives from
  one or more observations' results... not a value any lab measured
  directly." Its own doc already flags that this is **two different
  things under one heading**: "Derived measurements" (`cft`, `biot`,
  `vldl`, `nonhdl`, `ldlf`, `ldls`, `remnant` — concentrations of a
  real analyte, arrived at arithmetically instead of by assay — "A lab
  could equally have printed each of these as an observation") and
  "Indices proper" (HOMA-IR, AIP, TyG, TC/HDL, LDL/HDL, De Ritis, T/LH
  and the rest — ratios and scores, not quantities of a substance).

So Alex's instinct is already half-documented: the doc itself says
"Indices" is a heading over two different kinds of thing, and that
indices are *also* technically observations in the general clinical
sense (a computed result is still something observed about the
patient — LOINC has calculated-result codes of its own, see below).
The open question is whether the UI-facing split (and the
`INDEX_DEFS`/`IndexDef` internals) should reflect that.

## Is "Indices" the right word at all?

Literally, no — not for the whole set. `computed-index.md`'s own
breakdown makes this explicit:

- **Genuinely indices** (ratios/scores with no unit of substance, or a
  `%` unit): T/LH, DHT/T, T/E2, TC/HDL, LDL/HDL, De Ritis, HOMA-IR,
  AIP, TyG, FAI, TSAT, HOMA-B.
- **Not indices in the literal sense — estimated concentrations**:
  `cft` (calculated free T, pg/mL), `biot` (bioavailable T, nmol/L),
  `vldl`, `nonhdl`, `ldlf` (Friedewald LDL-C), `ldls` (Sampson LDL-C),
  `remnant`. These are mass or molar concentrations, same units as an
  observation — LDL-C is not "an index" any more than Hemoglobin is.

"Indices" is a decent name for the first group and a poor one for the
second. Whatever replaces it (or doesn't) should account for that
split, not paper over it with one word that's accurate for half the
contents.

## LOINC's own convention

Checked in this repo's own `web/public/data/analyses.json`: several of
the catalog's calculated codes carry **"by calculation"** literally in
their LOINC `longCommonName` — not a house convention, LOINC's own
naming:

- `13457-7` (Friedewald LDL-C, this catalog's `ldlf`): "Cholesterol in
  LDL [Mass/volume] in Serum or Plasma **by calculation**"
- HbA1c-calc equivalent: "Hemoglobin A1c/Hemoglobin.total in Blood
  **by calculation**"
- Globulin: "Globulin [Mass/volume] in Serum **by calculation**"

LOINC does not have a clean formal boolean property splitting
"measured" vs "calculated" results the way it has `PROPERTY` (e.g.
`MCnc`, `SCnc`) or `CLASS` — but its naming convention for a
calculated code is consistently to append "by calculation" to an
otherwise-ordinary long common name, i.e. LOINC treats a calculated
result as *the same kind of thing* (an observation) with a method
annotation, not as a separate category. That's a real data point in
favor of "calculated"/"calculation" as the adjective, and against
treating "index" as its own ontological tier — LOINC's own modeling
agrees with Alex's "I guess all of those are observations?" instinct.

## Naming options (no winner picked)

1. **Keep "Observations" / "Indices"** (status quo).
   Tradeoff: zero rename cost, but "Indices" is wrong for `ldlf`,
   `biot`, etc., and the doc already has to carve out a "two kinds
   under one heading" exception to explain it.

2. **"Measured" / "Calculated"** (Alex's first suggestion).
   Tradeoff: correctly describes *how the value was obtained*
   (assay vs. formula) rather than *what kind of thing it is*, matches
   LOINC's own "by calculation" convention, and reads naturally as a
   sentence ("this value was measured" / "this value was calculated")
   — but a section header reading "Calculated" over a table of ratios
   feels slightly odd compared to a noun like "Indices", and doesn't
   surface that some calculated values (`ldlf`) are directly
   comparable to a measured counterpart while others (T/LH) have none.

3. **"Analytes" / "Calculations"** (Alex's second suggestion).
   Tradeoff: "Analytes" is more precise than "Observations" for the
   measured side (an analyte is specifically a substance being
   quantified; not every observation is one — e.g. a qualitative
   result), but "Calculations" as a plural noun for the section reads
   awkwardly next to "Analytes" and is a bigger conceptual jump from
   the current internal name `INDEX_DEFS`/`computedIndices.ts` than
   "Calculated" would be.

4. **"Observed" / "Computed"** (a third pairing worth floating).
   Tradeoff: parallel adjectives, avoids "Indices" entirely, and
   "Computed" already exists in the codebase (`computed-index.md`,
   `computedIndices.ts`) so it's the least internally disruptive of
   the relabeling options — but "Observed" as a section header is a
   passive-voice noun-substitute that reads less naturally than
   "Observations" does today.

5. **Keep two tiers but rename only the mismatched half** — leave
   "Observations" alone, and split "Indices" into "Derived
   measurements" and "Indices" (or similar) as the doc's own internal
   two-kinds breakdown already suggests, rather than a single flat
   relabel.
   Tradeoff: fixes the actual inaccuracy (concentrations mislabeled as
   indices) without touching the observations side or the widely-used
   `INDEX_DEFS` internals at all — but introduces a three-tier UI
   (Observations / Derived measurements / Indices) where the app has
   shipped a clean two-tier one everywhere (grid cards, Results
   tables, Reference Book), which is a bigger structural change than
   a word swap, not a smaller one.

Every option above is a naming decision only — none of them changes
where an `ldlf`/`cft` collision with a lab-reported observation is
handled, which stays exactly as `computed-index.md` describes
regardless of what the section is called.

## Blast radius (from a grep of `web/src`, not exhaustively enumerated)

Renaming is not a copy tweak:

- The literal string `"Indices"` appears as UI copy in exactly one
  place worth calling out directly — the divider row label in
  `web/src/components/conditions/ResultTables.tsx:605` — but
  "Observations" (as a word, including "All Observations" the nav
  item/route/view name) turns up across roughly **18 files** in
  `web/src/components` alone: nav (`routing.ts`, `SideNav.tsx`,
  `NavBar.tsx`), the `AllObservationsView.tsx` component itself (a
  file name, not just a string), `PanelDetailView.tsx`,
  `PanelsGridView.tsx`, `ControlsBar.tsx`, and more.
- The internal identifiers run much deeper: `INDEX_DEFS`/`IndexDef`
  appear in roughly **14 files** (`indexDefs.ts`, `computedIndices.ts`
  and every view/hook that imports either — about **13 files** import
  from `computedIndices.ts` or `indexDefs.ts` directly), and the
  `Result` type (the in-memory shape backing an observation's value)
  touches roughly **24 files** — parsing, storage, export, every
  results-table view, the explore/chart adapters.
- Renaming *only UI copy* ("Indices" → "Calculated", say, as a label
  string) is cheap — one or two files. Renaming the *internal*
  vocabulary (`IndexDef`, `INDEX_DEFS`, `computedIndices.ts`,
  `AllObservationsView.tsx`) to match would touch dozens of files and
  is a much larger, separate decision that should not be assumed just
  because the UI copy changes — the doc/schema/test suite also refer
  to "index" throughout (`computed-index.md`,
  `pathway-reference-ranges-1.schema.json` prose, `INDEX_DEFS` test
  fixtures), so a full rename is a multi-file, multi-doc undertaking,
  not a string edit.

## Recommendation for scoping (not a naming decision)

Whatever is chosen, treat "change the UI-facing label" and "rename the
internal type/file vocabulary" as two separate, separately-schedulable
tasks — the first is low-risk copy; the second is a structural rename
across data/view/test files and should get its own task once (if) a
direction is picked.
