# Add an Experimental/Research Mode toggle for not-yet-clinically-established formulas

Alex's own words: "Advanced Approach (Dual-Mode): If you really want to
leverage the cutting-edge science of the Zakharov allosteric model, offer
it as an 'Experimental / Research Mode' toggle. Clearly add a tool-tip
explaining to the user that this is a modern, highly precise academic
model, but that its numbers should not be used to self-diagnose without a
doctor's oversight."

`parent_task: task-0024` because the motivating case (cFT-Z on Hormonal
Pathways) lives there, but the toggle concept itself is app-wide in
ambition — see "Open questions" below on whether it should generalize
beyond that one page/badge.

## The proposal

An opt-in "Experimental / Research Mode" toggle that gates any
formula/index the app implements but does not consider clinically
established (bleeding-edge academic model, not the Vermeulen-grade
default). When on, such a badge/value becomes visible; when off, it stays
hidden (or shown as "Not available" the way `unavailable: true` badges do
today). A tooltip on the toggle (and/or on the gated badge itself) states
plainly that this is a modern, high-precision academic model whose
numbers should not be used for self-diagnosis without a doctor's
oversight.

## What the code says: evidenceLevel vs. Experimental Mode

`web/src/data/indexDefs.ts`'s `IndexDef.evidenceLevel: string` (declared
`web/src/data/computedIndices.ts:268`) is populated today with exactly
`'heuristic' | 'consensus' | 'guideline'` and rendered as a colored pill
by `ReferenceBookPage.tsx`'s `EvidenceBadge`/`EVIDENCE_BADGE` map
(task-0044 documents this in full, including a vestigial unused `level`
field on the same interface — not this task's concern).

Reasoning on whether "experimental" extends that enum or is a separate
axis:

- `evidenceLevel` grades how well-established the underlying **science**
  is — is this formula's accuracy backed by guideline consensus, general
  clinical consensus, or is it a heuristic approximation? It answers "how
  much should a clinician trust this number," and it's populated per
  index regardless of whether the index is shown by default.
- "Experimental Mode" as Alex describes it is a **UI/product** axis —
  whether to compute-and-show a value at all without the viewer opting
  in first, independent of how it would eventually be graded once shown.
  A formula could in principle be `evidenceLevel: 'heuristic'` and shown
  by default (FAI already is, per task-0044) — heuristic isn't
  automatically experimental. Conversely a formula could be well-graded
  once verified but still ship behind the toggle for a period simply
  because it's new/unfamiliar to users.
- These look orthogonal, not the same axis: `evidenceLevel` is a
  property of the formula's evidence base; "experimental" is a property
  of the app's disclosure/consent posture toward showing it. Recommend
  keeping them as two separate fields rather than overloading
  `evidenceLevel` with a fourth value — collapsing them would force every
  future low-evidence-but-fine-to-show-by-default index (like FAI) to
  either dodge the "experimental" label or trigger a toggle it doesn't
  need.

## Open questions

- **Per-badge or app-wide?** A single global "Experimental Mode" switch
  (like a settings flag) is simpler to build and explain, but a per-badge
  flag (`experimental: true` on a `Badge`/`IndexDef`) is more flexible if
  only some formulas ever need it and others graduate out over time. Lean
  toward: one global toggle that *reveals* every badge/index flagged
  `experimental: true`, rather than N independent per-badge toggles —
  fewer settings to explain, and "Research Mode" reads as a single
  posture the user opts into, not a per-formula checklist. Not decided.
- **Where does it live, persistence-wise?** This is the same open
  question task-0042 is already working through for the albumin-fallback
  setting: is this a calculation-input-adjacent preference (closer to
  `envelopeMeta`, "how do I want my numbers computed/shown"), a display
  preference (`bloodtests_view_settings_v1`, alongside `compactPanels`),
  or its own persisted key? Cross-reference task-0042 directly before
  deciding — resolving "where do calculation-affecting toggles live" once
  should settle both tasks' placement rather than each inventing its own
  answer.
- **What triggers the tooltip?** Hover on the toggle, a dedicated info
  icon beside it, first-time-only (e.g. shown once on first enabling,
  never again), or persistent text under the toggle whenever it's on?
  Not decided — note that "not for self-diagnosis" is exactly the kind of
  warning that should probably be seen every time the toggle is flipped
  on, not just once, given the stakes Alex named.
- **Does off hide the badge, or also skip the computation?** This is a
  pure display gate, not a privacy or performance concern (worth stating
  explicitly since other toggles in this app sometimes affect what's
  computed) — recommend the value is still computed internally (so
  turning the toggle on/off is instant, no recompute), and only rendering
  is gated, mirroring how `unavailable: true` badges already render
  today when off.
- Does this toggle, once built, retroactively apply to the three already
  -`unavailable: true` cFT badges (Ly & Handelsman, Sartorius, Zakharov)
  the moment any one of them gets a real formula, or is that decided
  formula-by-formula?
