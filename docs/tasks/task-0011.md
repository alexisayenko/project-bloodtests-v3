# Normalize units to UCUM

Goal: a normalization pass that maps each observation's printed unit
to a canonical UCUM code, storing the canonical form in `unit` and the
string the lab printed in `rawUnit`. The target vocabulary is fixed in
[ADR-0007](../tech/decisions/adr-0007-ucum-as-the-unit-vocabulary.md);
what a unit is in this app, and why printed and canonical are two
different things, is in the [unit](../product/concepts/unit.md)
concept.

The problem is one of spelling, not of measurement: the same unit
arrives as `10^9/L`, `×10⁹/л`, `mmol/l` and `mmol/L` across years and
languages, and nothing today folds them together.

Approach:

- [x] Seed the mapping table from the per-code allowed-unit sets
      (`DEFAULT_UNITS` plus `ALLOWED_UNITS`, compared through
      `canonicalUnit`; they were hand-kept in
      `web/src/data/loincCheck.ts` then and are derived from the
      catalog in `web/src/data/analyteCatalog.ts` now). Those sets
      already encode which units a LOINC code may carry — they exist
      to disambiguate codes, and they are the seed of the
      normalization table. The dimension check reads them directly
      rather than copying them.
- [x] The derivation itself, in `web/src/data/unitNormalization.ts`:
      three pure stages — printed unit (Cyrillic and Ukrainian
      tables, superscripts, micro and multiplication signs) to a
      canonical Latin spelling, Latin to UCUM, then a
      code-versus-unit dimension check — plus `convertValue`,
      `canonicalUnitFor` and a `normalizeObservationUnit`
      orchestrator. Nothing is stored and nothing is mutated; an
      unrecognized unit returns undefined rather than a guess.
      Covered by `web/test/unit-normalization.test.ts`.
- [x] The mass/molar case, which turned out to be the sharp one: a
      molar unit under a mass-concentration code is a *code* error,
      so the check names the analyte's `[Moles/volume]` sibling
      instead of converting the number ([ADR-0003](../tech/decisions/adr-0003-store-only-what-the-lab-printed.md)).
      20 curated pairs in `web/src/data/massMolarSiblings.ts`; their
      molar codes added to the analyte catalog
      (`web/public/data/analyses.json`, 124 → 139 then, 159 now) and
      aliased to their mass primary in `ALSO_REFS` / `ALIAS_TO_PRIMARY`, so
      panels, tables and charts needed no changes.
      `web/scripts/recode-molar.mjs` applies the same repair to a
      file offline, rewriting only `loinc`.
- [ ] Parse and validate against UCUM with the National Library of
      Medicine's JavaScript UCUM library — the same source the app
      already calls for the online LOINC lookup. Deferred, not
      dropped: the curated tables are a subset, not a parser, and
      [task-0008](task-0008.md) is still the upgrade path.
- [x] Wire it into the import path. `web/src/data/parseUpload.ts` —
      the single route every import takes (chatbot JSON, Import JSON,
      share link) — runs `normalizeObservationUnit` over every
      observation. The printed `value`/`unit` are kept exactly as
      read; where the unit places cleanly and the conversion to the
      code's canonical UCUM unit is known, the derived pair is
      attached to the in-memory `Result` as an optional `canonical`
      field. It is derived, not reported: the exporter's
      field-by-field mapping never emits it, so an
      import-then-export round trip is byte-identical.
      `web/src/data/validateDiagnosticReports.ts` surfaces the two
      cases that cannot be resolved silently — a dimension
      contradiction with a known sibling code (warning naming
      printed unit, current code and sibling) and an unmappable unit
      (lower-severity warning, the signal that the curated tables
      need extending) — on the Diagnostic Reports table's existing
      warning dot and in the report detail view.
- [ ] Surface results as confirmable suggestions in the Diagnostic
      Report detail view, alongside the existing LOINC cross-check,
      reusing its suggestion-chip and "Apply suggestions" mechanics.
      Never a silent rewrite of what the lab printed. Warnings land
      today; the one-click repair does not.
- [ ] Consolidate the catalog: the sibling pairs, `ALSO_REFS` and the
      per-code allowed-unit sets now state overlapping facts about
      which unit belongs to which code, in three places. Two of the
      three folded into `web/public/data/analyses.json` with
      [ADR-0010](../tech/decisions/adr-0010-analyte-catalog-is-the-source-of-truth.md)
      — `ALSO_REFS` and the allowed-unit sets are derived from the
      catalog now, not hand-kept. `massMolarSiblings.ts` still carries
      its own `unit` per code, so the third copy stands. What did fold
      in there is the *factor*, a separate duplication of the same kind
      found on the way: each pair's `massPerMolarUnit` and
      `computedIndices.ts`'s eight hand-typed constants are now derived
      from `web/public/data/molar-masses.json`
      ([ADR-0011](../tech/decisions/adr-0011-molar-masses-are-data-factors-are-derived.md)),
      which leaves the unit as the only fact the pairs still restate.
- [ ] Export then writes both fields: canonical `unit`, printed
      `rawUnit`.

Settled: normalization runs **at import**, not in a report view. The
objection to import-time — that it rewrites data the user hasn't
looked at — turned out not to apply, because nothing is rewritten:
the printed pair is kept verbatim and the canonical form is attached
beside it. What cannot be derived is reported as a warning rather
than resolved, so the confirm step stays in front of every actual
change to the file.
