# Normalize units to UCUM

Goal: a normalization pass that maps each observation's printed unit
to a canonical UCUM code, storing the canonical form in `unit` and the
string the lab printed in `rawUnit`. The target vocabulary is fixed in
[ADR-0007](../tech/decisions/adr-0007-ucum-as-the-unit-vocabulary.md);
what a unit is in this app, and why printed and canonical are two
different things, is in the [unit](../product/concepts/unit.md)
concept.

The problem is one of spelling, not of measurement: the same unit
arrives as `10^9/L`, `×10⁹/л`, `mmol/l` and `mmol/L` across years and
languages, and nothing today folds them together.

Approach:

- [x] Seed the mapping table from the per-code allowed-unit sets
      (`DEFAULT_UNITS` plus `ALLOWED_UNITS`, compared through
      `canonicalUnit`; they were hand-kept in
      `web/src/data/loincCheck.ts` then and are derived from the
      catalog in `web/src/data/analyteCatalog.ts` now). Those sets
      already encode which units a LOINC code may carry — they exist
      to disambiguate codes, and they are the seed of the
      normalization table. The dimension check reads them directly
      rather than copying them.
- [x] The derivation itself, in `web/src/data/unitNormalization.ts`:
      three pure stages — printed unit (Cyrillic and Ukrainian
      tables, superscripts, micro and multiplication signs) to a
      canonical Latin spelling, Latin to UCUM, then a
      code-versus-unit dimension check — plus `convertValue`,
      `canonicalUnitFor` and a `normalizeObservationUnit`
      orchestrator. Nothing is stored and nothing is mutated; an
      unrecognized unit returns undefined rather than a guess.
      Covered by `web/test/unit-normalization.test.ts`.
- [x] The mass/molar case, which turned out to be the sharp one: a
      molar unit under a mass-concentration code is a *code* error,
      so the check names the analyte's `[Moles/volume]` sibling
      instead of converting the number ([ADR-0003](../tech/decisions/adr-0003-store-only-what-the-lab-printed.md)).
      21 curated pairs in `web/src/data/massMolarSiblings.ts`; their
      molar codes added to the analyte catalog
      (`web/public/data/analyses.json`, 124 → 139 then, 163 now) and
      aliased to their mass primary in `ALSO_REFS` / `ALIAS_TO_PRIMARY`, so
      panels, tables and charts needed no changes.
      `web/scripts/recode-molar.mjs` applies the same repair to a
      file offline, rewriting only `loinc`.
      The pairs' derived factor has since gained its one legitimate use,
      which is not this box's: at *display* time, the "What's in range"
      chart puts a history that crosses the divide onto its band's single
      scale, and an index places a molar-alias input into the unit its
      formula declares. Neither stores or exports anything, so ADR-0003
      is untouched — but it means the mass/molar case is now visibly
      handled everywhere except the one place this task is still open,
      the file itself.
- [x] Wire it into the import path. `web/src/data/parseUpload.ts` —
      the single route every import takes (chatbot JSON, Import JSON,
      share link) — runs `normalizeObservationUnit` over every
      observation. The printed `value`/`unit` are kept exactly as
      read; where the unit places cleanly and the conversion to the
      code's canonical UCUM unit is known, the derived pair is
      attached to the in-memory `Result` as an optional `canonical`
      field. It is a converted *value*: derived, not reported, so the
      exporter's field-by-field mapping never emits it.
      `web/src/data/validateDiagnosticReports.ts` surfaces the two
      cases that cannot be resolved silently — a dimension
      contradiction with a known sibling code (warning naming
      printed unit, current code and sibling) and an unmappable unit
      (lower-severity warning, the signal that the curated tables
      need extending) — on the Diagnostic Reports table's existing
      warning dot and in the report detail view.
- [x] Surface results as confirmable suggestions in the Diagnostic
      Report detail view, alongside the existing LOINC cross-check,
      reusing its suggestion-chip mechanics. `unitRepairFor`
      (`web/src/components/conditions/reportDetailHelpers.ts`) re-runs
      `normalizeObservationUnit` per row and, where the dimension check
      contradicts the code and the sibling table knows the code on the
      printed scale, feeds that sibling into the existing chip row as a
      third source beside the offline resolver's and the NLM lookup's.
      Clicking it changes the `loinc` and nothing else — the value and
      the printed unit are what the lab reported (ADR-0003) — through
      the same edit draft and the same Save/Cancel gate the LOINC chips
      use. Deliberately *not* auto-applied the way a confident LOINC fix
      is: these warnings render on mount, so auto-applying would mutate
      the draft on page load, and which of the two the lab got wrong is
      a judgement rather than a derivation. The unmappable-unit warning
      gets no chip, because there is nothing to suggest — that one is
      still a warning and only a warning.
- [x] Consolidate the catalog: the sibling pairs, `ALSO_REFS` and the
      per-code allowed-unit sets stated overlapping facts about
      which unit belongs to which code, in three places. Two of the
      three folded into `web/public/data/analyses.json` with
      [ADR-0010](../tech/decisions/adr-0010-analyte-catalog-is-the-source-of-truth.md)
      — `ALSO_REFS` and the allowed-unit sets are derived from the
      catalog now, not hand-kept. The third copy is gone too: a
      `massMolarSiblings.ts` code declares only `{loinc,
      longCommonName}` and takes its unit from `DEFAULT_UNITS` through
      `withUnit()`, which throws naming the code rather than deriving a
      factor from an undefined unit. Two things surfaced doing it — the
      catalog spelled eight microgram units `mcg/…` and one `µg/mL`
      where the app's canonical Latin form is `ug/…` (and `mcg` breaks
      `concentrationScale`'s prefix parsing), and three molar sibling
      codes were missing from the catalog entirely (`14749-6` glucose,
      `22664-7` urea, `14798-3` iron); both were fixed, taking the
      catalog to 163 entries. What folded in earlier was the *factor*, a
      separate duplication of the same kind found on the way: each
      pair's `massPerMolarUnit` and
      `computedIndices.ts`'s eight hand-typed constants are now derived
      from `web/public/data/molar-masses.json`
      ([ADR-0011](../tech/decisions/adr-0011-molar-masses-are-data-factors-are-derived.md)),
      leaving the unit, which this box then took.
- [x] Export then writes both fields: canonical `unit`, printed
      `rawUnit`. `exportData.ts` folds the printed spelling through
      `ucumUnitFor` into `unit` and writes the printed string to
      `rawUnit` whenever a unit was printed at all; a unit the curated
      tables cannot place leaves `unit` **absent** rather than filled
      with the printed string, which would claim a normalization that
      did not happen. Spelling only — no value is converted, so ADR-0003
      holds. `parseUpload.ts` reads `rawUnit` in preference to `unit`,
      so the app goes on displaying and validating what the lab printed.
      The published schema and the generated types were updated with it.

Settled: normalization runs **at import**, not in a report view. The
objection to import-time — that it rewrites data the user hasn't
looked at — turned out not to apply, because nothing is rewritten:
the printed pair is kept verbatim and the canonical form is attached
beside it. What cannot be derived is reported as a warning rather
than resolved, so the confirm step stays in front of every actual
change to the file.

Handed off, not dropped: parsing and validating against the NLM's
JavaScript UCUM library was listed here from the start and decided
against every time it came up — the curated tables are a subset, not a
parser, but adopting a parser is a dependency and a lift of its own,
with its own triggers. It is [task-0008](task-0008.md)'s, and this task
closes without it rather than staying open forever on a box it had
already decided it would not do.

What normalization writes today is the unit's *spelling*. Converting a
value still belongs at display time (ADR-0003), and the two cases the
derivation cannot settle stay in front of a person: the mass/molar one
as a repair chip, the unplaceable unit as the warning that says the
curated tables need extending.
