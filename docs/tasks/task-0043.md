# Add a show/hide toggle for the Scheduled block in results tables

## The problem

The Scheduled block (one column per scheduled visit, plus a trailing
"add a visit" column) renders unconditionally in every results table, in
both Panel Detail's Results tab and All Observations. There is no way to
hide it, even for someone who isn't actively scheduling anything and just
wants a narrower table.

## What the code says

- `web/src/components/conditions/ResultTables.tsx`: `ResultsTable`'s
  `showScheduling` (line 563) is computed as `Boolean(onAddVisit)` — the
  block's visibility is driven entirely by whether the caller passes an
  `onAddVisit` handler, not by whether any visit exists. `gridWidth`
  (line 103) adds `GAP_COL_WIDTH + visitCount * SCHEDULED_COL_WIDTH +
  ADD_COL_WIDTH` to the table width whenever `showScheduling` is true, so
  hiding the block would also narrow the table, per the request.
- Both callers always pass `onAddVisit`: `PanelDetailView.tsx` (line 164)
  and `AllObservationsView.tsx` (line 199) pass it unconditionally, so
  `showScheduling` is unconditionally `true` in both views today — the
  block is always shown once a panel or the observations table renders,
  even with zero visits (per repo CLAUDE.md, a table with nothing
  scheduled still renders the trailing "add a visit" column, no visit
  columns).
- There is no existing show/hide control anywhere for this block — no
  prop, no setting, no UI toggle. This is a net-new control, not a wiring
  fix.
- `ControlsBar.tsx` is the established home for this kind of per-table
  display control (`ControlGroup` + a control, e.g. `SegmentedControl` for
  unit system / sample limit, a `<select>` for panel filter, a search box
  for marker query) and already renders identically in both Panel Detail
  and All Observations, so a toggle added there would appear in both
  views with no extra wiring per view.

## The proposal

Add a toggle to show or hide the Scheduled block/columns entirely,
presumably to reduce table width/clutter when the user isn't actively
scheduling. Likely shape: a boolean threaded from wherever it's decided
to live, through the view, into `ResultsTable`'s existing `showScheduling`
computation (probably `Boolean(onAddVisit) && showScheduled` or similar —
`onAddVisit` would still need to be passed down for the handler to exist,
but gated by the new toggle).

## Open questions

- **Persisted or session-only?** `compactPanels`/`unitSystem`/
  `sampleLimit` persist in `bloodtests_view_settings_v1`
  (`ui.ts`'s `loadViewSettings`/`saveViewSettings`), carried through
  Clear all data and the backup's `settings.json`. The panel filter and
  marker query, by contrast, are deliberately session-only `useState` in
  each view, per repo CLAUDE.md: "`ControlsBar` holds no state: each view
  keeps its filter in `useState`... deliberately not lifting it to the
  shell, which owns the *persisted* settings." A Scheduled-block toggle
  reads more like the former (a durable display preference someone sets
  once) than the latter (a transient filter) — but not decided.
- **Does hiding Scheduled also hide the "add a visit" column, or just the
  existing visit columns?** Hiding everything is simpler and matches
  "reduce clutter," but removes the only entry point for adding a visit
  from that table (the add affordance lives only in the results tables
  today, per repo CLAUDE.md's Scheduled Visits page notes). Keeping the
  add column while hiding populated visit columns is more useful but
  changes `showScheduling`'s current all-or-nothing semantics and needs
  its own width/colgroup handling in `ResultTables.tsx`.
- **Same behavior in both views, or could it differ?** `ControlsBar`
  already renders identically in Panel Detail and All Observations, so
  the natural default is one shared toggle affecting both. Worth
  confirming there's no reason (e.g. Panel Detail being the more
  scheduling-focused workflow) to let them diverge.
