# Add a collapsible FBC group to reduce marker-row noise (FBC only, not a generic mechanism)

## The problem

FBC (Full Blood Count, aka CBC) is defined in `web/public/data/panels.json`
as the laboratory panel `fbc`, with three sections — Leukocytes and
Differentials (12 LOINCs), Erythrocytes (8 LOINCs), Platelets (6 LOINCs) —
26 LOINCs in total. `web/public/data/monitoring-panels.json`'s "FBC" entry
is a straight pass-through of that laboratory panel (`panelId: "fbc"`, no
`extraLoincs`/`excludeLoincs`), so the Monitoring Panels grid card for FBC
carries all 26 as separate observation rows.

That noise is experienced in two places, both confirmed by reading the
code, not assumed:

1. **The Scheduled column checkboxes in the results tables**
   (`web/src/components/conditions/ResultTables.tsx`) — this is where
   markers actually get added to a visit. `ResultsTable` renders one
   `ScheduledCell` (one checkbox) per observation row, with no grouping of
   any kind. Both Panel Detail's FBC table and All Observations show all
   26 FBC rows this way when FBC markers are present.
2. **The Scheduled Visits page**
   (`web/src/components/conditions/PlanVisitView.tsx`) — `VisitPlanCard`
   calls `planRows(visit.loincs)` and renders one table row per LOINC, again
   with no grouping. A visit with a full FBC scheduled shows all 26 rows
   inline among whatever else is scheduled for that visit.

So the noise is real on both surfaces — the point of entry (results-table
checkboxes) and the summary/pricing view (Scheduled Visits) — and a fix
needs to consider both, since collapsing only one still leaves the other
noisy.

## Scope decision (deliberate, read before implementing)

Alex considered a generic "expandable panel group" mechanism first —
collapsed by default, expand to see/toggle individual markers — and
immediately spotted a real unresolved problem with it (see below). He then
considered a broader "Lab Packages" abstraction, since FBC isn't the only
multi-marker bundle a lab sells as one order — coagulogram and leukoformula
were named as other examples, each with its own bundling quirks — but
**explicitly decided against building a generic/universal solution now**,
because it isn't yet known whether one generic model would actually fit all
these different bundle types well.

**This task is scoped to FBC specifically. It is not a "Lab Packages"
system.** Don't generalize while implementing — that generalization is
premature until more bundle types are understood, and is deliberately left
for a later task if/when it turns out to be warranted.

## Open problem this task does NOT solve: partial selection

If FBC becomes a collapsed, expandable group, and the user expands it and
selects only some of its 26 markers, the app cannot assume a laboratory can
actually fulfill a partial FBC order — in practice a lab draws and prices
FBC as one whole panel, not a build-your-own-basket of its markers. This is
a genuine open design question, not something this task resolves. Options
to weigh at design time (none picked here):

1. Selecting any FBC marker auto-selects the whole group, with no partial
   selection allowed at all — simplest, matches how a lab actually orders
   it, but loses the ability to schedule (say) just RBC-related markers
   when that's really what's wanted.
2. Allow partial selection in the UI, and treat fulfillment/pricing
   accuracy as a separate, later concern — simpler to build now, but risks
   showing a plan that doesn't reflect what a lab will actually do or
   charge.
3. Some hybrid — e.g. partial selection allowed, but the UI visibly warns
   or annotates that a lab may not offer less than the full panel.

## Where FBC's marker list comes from

Don't invent a marker list for "FBC" — use the existing laboratory-panel
definition. `web/public/data/panels.json`'s `fbc` entry (id `fbc`, name
"Full Blood Count (FBC)") is the source of truth for which 26 LOINCs count
as FBC, already split into three named sections (Leukocytes and
Differentials, Erythrocytes, Platelets) that could plausibly double as the
collapsed group's own sub-structure if that turns out to be useful.
`web/public/data/monitoring-panels.json`'s "FBC" monitoring panel just
points at this same `panelId: "fbc"` with no additions or exclusions, so
the monitoring-panel layer doesn't need to be touched to find the list —
only consulted, from `panels.json`, wherever the collapsing UI needs it.
